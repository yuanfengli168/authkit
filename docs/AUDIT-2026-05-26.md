# AuthKit Deep Audit Report

**Date:** 2026-05-26  
**Auditor:** openAI:gpt-oss-120b  
**Summary:** Deep audit of AuthKit repo — found 5 critical, 3 high, and 10 medium bugs affecting consumers who import this library.

---

## 🔴 CRITICAL BUGS

### Bug 1: Modal renders with empty providers and null auth — `show()` ignores its arguments
**File:** `ui/modal.js` (lines 108-113) and `core/authkit.js` (lines 119-123, 131-136)

`createModal()` returns `{ show, hide, update }`. The `show()` function accepts **zero parameters** — it reads `_providers` and `_auth` from its closure. However, `authkit.js` calls `_modal.show(_providers, auth, emailProvider)`, passing 3 arguments that are **silently ignored**. Crucially, `update()` (which sets `_providers` and `_auth`) is **never called** for modal mode — it's only called for inline mode. This means `_providers` stays `[]` and `_auth` stays `null` when `buildModal()` runs, producing an **empty modal with no sign-in buttons and a null auth reference**.

**Impact:** The login modal will be completely non-functional — no provider buttons, no email form, and any sign-in attempt will crash with a null reference error.

**Fix:** Call `_modal.update(_providers, auth)` before `_modal.show()` in `authkit.js`, or make `show()` accept and forward parameters.

### Bug 2: Modal CSS selectors don't match — overlay styles never apply
**File:** `ui/modal.js` (CSS lines 1-65) and `buildModal()` (line ~80)

All modal CSS selectors use `[data-authkit] .ak-overlay`, requiring `.ak-overlay` to be a **descendant** of an element with `data-authkit`. However, the overlay is appended to `document.body` and has `data-authkit` on **itself** — not on a parent. An element is not its own descendant, so these selectors never match the overlay element itself.

The overlay will lack: `position: fixed`, `inset: 0`, `background`, `z-index`, `display: flex` — making the modal completely broken visually.

**Impact:** The modal overlay renders as an unstyled `<div>` at the bottom of `<body>`. No overlay background, no centering, no z-index. The modal is effectively invisible/broken.

**Fix:** Change CSS selectors to include the case where the element itself has `data-authkit`:
```css
[data-authkit] .ak-overlay,
.ak-overlay[data-authkit] { ... }
```

### Bug 3: Modal reads config from wrong location (`config.theme` vs `config.ui.theme`)
**File:** `ui/modal.js` (lines ~85-100), `ui/inline.js` (lines ~45-50)

The modal reads `config.logoUrl`, `config.brandEmoji`, `config.loginTitle`, `config.brandName`, `config.theme`, and `config.googleAuthMode` from the top level. However, `mergeConfig()` merges defaults so that `brandName`, `logoUrl`, and `theme` live under `config.ui.*`. After merging, `config.brandName` is `undefined` while `config.ui.brandName` is `''`.

**Impact:** The modal will always display "Sign in to continue" instead of the configured brand name, won't show a logo, and won't apply the correct theme (dark/light/auto).

**Fix:** Read from the correct nested path:
```js
const ui = config.ui ?? {};
const brandName = ui.brandName || config.brandName || '';
const logoUrl = ui.logoUrl ?? config.logoUrl ?? null;
const theme = ui.theme ?? config.theme ?? 'auto';
```

### Bug 4: `signOut()` dispatches `SIGN_OUT` before Firebase sign-out — state stuck in `loading` on failure
**File:** `core/authkit.js` (lines 103-108)

`dispatch({ type: 'SIGN_OUT' })` sets state to `loading` **before** `await signOut(getAuth_())` completes. If `signOut()` throws (network error, etc.), the state machine is stuck in `loading` forever because `SIGN_OUT_COMPLETE` is only dispatched by `onAuthStateChanged` when the user actually signs out.

**Impact:** If Firebase `signOut()` fails, the entire UI is stuck in a loading state with no way to recover except a page reload.

**Fix:** Add error handling:
```js
async signOut() {
  const { signOut } = await import(`...firebase-auth.js`);
  try {
    await signOut(getAuth_());
  } catch (e) {
    dispatch({ type: 'CLEAR_ERROR' }); // recover from loading
    throw e;
  }
},
```

### Bug 5: `requireAuth()` causes infinite redirect loop on login page
**File:** `core/authkit.js` (lines 110-118)

`requireAuth()` redirects to `loginPage` with a `redirect` parameter pointing back to the current URL. If `requireAuth()` is called on the login page itself, it redirects to the login page again, creating an infinite loop.

**Impact:** Any page that calls `requireAuth()` while already on the login page will enter an infinite redirect loop.

**Fix:** Detect if already on the login page:
```js
if (location.pathname === new URL(loginPage, location.origin).pathname) return false;
```

## 🟠 HIGH SEVERITY BUGS

### Bug 6: No guard against double `init()` — duplicate subscriptions, DOM elements, and Firebase instances
**File:** `core/authkit.js` (lines 42-98)

Calling `AuthKit.init()` twice creates duplicate Firebase `onAuthStateChanged` listeners, duplicate state subscriptions, duplicate CSS injections, and duplicate `data-authkit` attributes on the anchor. Old subscriptions are never cleaned up.

**Impact:** If `init()` is accidentally called twice (common in SPA hot-reloading or React strict mode), consumers get duplicate UI updates, duplicate redirects, and memory leaks.

**Fix:** Add a guard:
```js
let _initialized = false;
async init(userConfig) {
  if (_initialized) { console.warn('[AuthKit] Already initialized.'); return AuthKit; }
  _initialized = true;
  // ...
},
```

---

### Bug 7: `onAuthStateChanged` never fires for initial unauthenticated state
**File:** `core/authkit.js` (lines 73-80)

`onAuthStateChanged(cb)` uses reference equality (`current !== prev`) to decide whether to call the callback. Since `prev` starts as `null` and `current` is also `null` when unauthenticated, `null !== null` is `false`, so the callback is **never called** for the initial unauthenticated state.

**Impact:** Consumers who rely on `onAuthStateChanged` to get the initial auth state will never receive a callback when the user is signed out.

**Fix:** Use a sentinel value:
```js
onAuthStateChanged(cb) {
  let prev = undefined;
  return subscribe((state) => {
    const current = state.user ?? null;
    if (current !== prev || prev === undefined) {
      prev = current;
      cb(current);
    }
  });
},
```

### Bug 8: `showLogin()`, `signOut()`, `renderSettings()` silently fail or crash if called before `init()`
**File:** `core/authkit.js` (lines 103-130)

`showLogin()` checks `if (_modal)` but if `_modal` is null (init not called), it silently does nothing. `signOut()` calls `getAuth_()` which returns `null`, causing `signOut(null)` to throw. `renderSettings()` passes `null` for `_config`, `getAuth_()`, and `getApp_()`.

**Impact:** Calling any method before `init()` either silently fails or throws an unhelpful error.

**Fix:** Add guards:
```js
showLogin() { if (!_config) throw new Error('[AuthKit] Call init() first.'); ... },
async signOut() { if (!getAuth_()) throw new Error('[AuthKit] Call init() first.'); ... },
```

## 🟡 MEDIUM SEVERITY BUGS

### Bug 9: Double state notification in redirect mode
**File:** `core/session.js` (lines 28-35, 38-44)

In redirect mode, `getRedirectResult()` dispatches `AUTH_SUCCESS`, then `onAuthStateChanged` fires and dispatches `AUTH_SUCCESS` again. Subscribers receive two notifications for the same event.

**Impact:** Duplicate callbacks to subscribers — could cause double redirects or double UI updates.

---

### Bug 10: Memory leak — modal's state subscription never unsubscribed after auto-hide
**File:** `ui/modal.js` (lines ~100-105)

`buildModal()` subscribes to state changes to auto-hide on auth success, storing the unsubscribe in `_unsubState`. But `hide()` never calls `_unsubState()`. The subscription persists for the page lifetime.

**Impact:** Minor memory leak; `hide()` is idempotent so no functional breakage, but unnecessary work on every state change.

---

### Bug 11: Memory leak — settings page logout redirect subscription never unsubscribed
**File:** `ui/settings.js` (lines ~85-89)

The `subscribe()` at the end of `render()` for redirect-on-logout is never unsubscribed. If `render()` is called multiple times, subscriptions accumulate.

**Impact:** Multiple redirect attempts on logout.

---

### Bug 12: Duplicate state subscriptions in inline mode
**File:** `core/authkit.js` (lines 88-91) and `ui/inline.js` (lines ~70-76)

In `authkit.js`, a subscription is created for show/hide. Inside `createInline.render()`, another subscription does the same thing. Both fire on every state change, causing `show()`/`hide()` to be called twice.

**Impact:** Double execution of show/hide on every auth state change.

---

### Bug 13: `hide()`/`show()` race condition in modal
**File:** `ui/modal.js` (lines ~115-125)

`hide()` uses `setTimeout` with 200ms delay to set `display: none`. If `show()` is called within that 200ms window, the `setTimeout` callback will set `display: none` on the now-visible overlay.

**Impact:** Modal can disappear if quickly closed and reopened.

**Fix:** Clear the timeout in `show()`:
```js
let _hideTimeout = null;
function hide() { _hideTimeout = setTimeout(...); }
function show() { clearTimeout(_hideTimeout); ... }
```

---

### Bug 14: XSS risk via `innerHTML` with provider icons
**File:** `ui/components/provider-button.js` (line 8), `ui/components/connected-section.js` (line 22)

`ce('span', { innerHTML: provider.icon })` uses `innerHTML` directly. If a consumer registers a custom provider with a malicious `icon` string containing `<script>` or event handlers, it would execute arbitrary JavaScript.

**Impact:** XSS vulnerability if custom providers are registered with untrusted icon content.

---

### Bug 15: Path traversal in provider loading
**File:** `core/registry.js` (line 16)

`loadProvider(id)` constructs a URL as `${baseUrl}/providers/${id}.js` without sanitizing `id`. A malicious `id` like `../../core/state` could load an unintended module.

**Impact:** If `enabledProviders` comes from user input or a compromised config, arbitrary modules could be loaded.

**Fix:** Validate the provider ID:
```js
if (!/^[a-z0-9_-]+$/i.test(id)) throw new Error(`[AuthKit] Invalid provider id: "${id}"`);
```

---

### Bug 16: `navigator.clipboard.writeText()` fails in non-HTTPS contexts
**File:** `ui/components/saved-keys-section.js` (line ~68)

`navigator.clipboard.writeText()` is only available in secure contexts (HTTPS). In HTTP environments, it throws a `TypeError`. No error handling or fallback.

**Impact:** Clicking the copy button on HTTP sites throws an unhandled error.

---

### Bug 17: `account-section.js` — `updateProfile` uses `auth.currentUser` which can be null
**File:** `ui/components/account-section.js` (line ~40)

`updateProfile(auth.currentUser, ...)` is called when the user clicks Save. If the user signs out in another tab or the session expires between rendering and clicking Save, `auth.currentUser` is `null`, causing `updateProfile` to throw.

**Impact:** Unhandled error when saving profile if the user is no longer authenticated.

---

### Bug 18: `deleteUserData` is not atomic — partial deletion possible
**File:** `core/firestore.js` (lines 43-53)

`deleteUserData()` first deletes all keys, then deletes the user document. If the user document deletion fails, the keys are already gone but the user document remains. No rollback or transaction.

**Impact:** Data inconsistency — user's saved keys are deleted but the user document still exists.
